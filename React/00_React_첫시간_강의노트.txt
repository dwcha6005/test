▶ 질문 던지기
  "지금까지 배운 바닐라 JS와 jQuery로 인스타그램을 만든다면 어디가 제일 힘들까?"

  기대하는 대답 / 유도
  - 좋아요를 누르면 : 하트 색, 좋아요 숫자, 알림 숫자, 내 활동 목록 ... 여러 곳을 다 고쳐야 한다.
  - 피드가 무한 스크롤로 계속 추가된다 → 이벤트 위임, 요소 생성 코드가 끝없이 늘어난다.
  - 같은 카드 모양(게시물)을 여러 화면에서 쓰는데, 복사 붙여넣기 하면 수정할 때 다 고쳐야 한다.

  → 오늘의 결론을 먼저 말해 둔다.
    "React는 '데이터가 바뀌면 화면을 어떻게 고칠지'를 우리가 아니라 React가 하게 만든 도구다."

2. 웹 개발의 역사 - React 이전 (10분)
=====================================================================
판서용 연표

  1991   웹의 시작         HTML 문서 = 정적인 페이지
  1995   JavaScript 탄생    버튼 클릭 정도의 간단한 동작
  2000년대 초  서버 렌더링   PHP, JSP, ASP : 서버가 HTML을 완성해서 보냄
                            → 링크/버튼을 누를 때마다 "페이지 전체 새로고침"
  2004~2005  AJAX의 유행   Gmail, Google Maps
                            → 새로고침 없이 데이터만 받아서 화면 일부를 바꾼다 (14_fetch에서 배운 것)
  2006   jQuery            브라우저마다 다른 DOM 사용법을 통일, 짧은 문법 (16_jquery)
  2010   Backbone.js, AngularJS 등 "프론트엔드 프레임워크" 등장
  2013   React 공개
  2014~  Vue.js, 이후 Svelte 등


< 2-1. 서버 렌더링 시대 >
  - 화면을 바꾸려면 서버에 다시 요청 → HTML 전체를 다시 받는다.
  - 사용자 입장 : 클릭할 때마다 하얀 화면 깜빡임, 스크롤 위치 초기화, 입력하던 내용 사라짐

< 2-2. AJAX + jQuery 시대 >
  - 데이터만 받아 오고, 화면은 JS로 직접 고친다. → 웹이 "앱"처럼 동작하기 시작
  - 문제 : 화면을 고치는 코드를 사람이 전부 직접 써야 한다. (명령형, Imperative)

    // 좋아요 버튼 하나에 필요한 코드 (jQuery)
    $("#likeBtn").on("click", function () {
        liked = !liked;
        likeCount += liked ? 1 : -1;
        $(this).toggleClass("on");                         // 하트 색
        $("#likeCount").text(likeCount);                    // 게시물의 숫자
        $("#myLikes").text(myLikeTotal());                  // 내 프로필의 숫자
        if (liked) $("#activity").prepend("<li>...</li>");  // 활동 목록
        else $("#activity li[data-id=" + id + "]").remove();
    });

  - 기능이 100개가 되면?
    "이 데이터가 바뀌면 화면의 어디 어디를 고쳐야 하지?"를 사람이 다 기억해야 한다.
    → 하나라도 빠뜨리면 화면과 실제 데이터가 다른 버그가 생긴다.
    → 이런 코드를 "스파게티 코드"라고 부른다. (서로 얽혀서 하나를 당기면 다 따라 나온다)

< 2-3. 1세대 프레임워크 >
  - Backbone.js : 데이터(Model)와 화면(View)을 나누는 구조를 제공
  - AngularJS   : 양방향 데이터 바인딩 - 데이터와 화면이 자동으로 서로를 바꾼다.
                  편리했지만, 앱이 커지면 "누가 무엇을 바꿨는지" 추적이 어렵고 느려지는 문제가 있었다.

3. React의 탄생 - Facebook이 겪은 문제 (7분)
=====================================================================
< 문제 상황 >
  - Facebook은 한 화면에 같은 데이터가 여러 곳에 표시된다.
    예) 읽지 않은 메시지 수 : 상단 아이콘, 채팅창, 메시지 페이지
  - 실제로 "메시지를 다 읽었는데도 알림 숫자가 남아 있는" 같은 버그가 반복해서 생겼고,
    고쳐도 다른 곳에서 다시 생겼다.
  - 원인 : 데이터가 바뀔 때 화면을 고치는 코드를 사람이 곳곳에 직접 작성했기 때문 (2-2의 문제)

< 해결 아이디어 >
  Facebook 개발자 조던 워크(Jordan Walke)의 발상

    "화면 일부를 골라서 고치지 말자.
     데이터가 바뀌면 그냥 화면 전체를 처음부터 다시 그린다고 생각하자."

  - 서버 렌더링 시절처럼 "데이터 → 화면을 통째로 다시 만든다"는 단순한 사고방식
  - 하지만 실제로 DOM 전체를 다시 만들면 느리고, 입력 중인 내용과 스크롤이 날아간다.
  - 그래서 "가상의 화면(Virtual DOM)을 다시 그려 보고, 실제 DOM에는 바뀐 부분만 반영"한다.
    → 개발자는 "전체를 다시 그린다"고 생각하고 코드를 쓰고, 최적화는 React가 한다.

< 연표 >
  2011   Facebook 뉴스피드에 처음 적용
  2012   Instagram 웹에 적용
  2013   오픈 소스로 공개 (JSConf US)
         → 처음에는 반응이 나빴다. "JS 안에 HTML을 섞다니, 관심사 분리 원칙 위반이다!"
         → React 팀의 반론 : "기술(HTML/CSS/JS)로 나누지 말고 기능(컴포넌트)으로 나누자"
  2015   React Native 공개 (같은 방식으로 모바일 앱 개발)
  2019   Hooks 등장 (React 16.8) - 함수 컴포넌트 + useState, useEffect → 지금 우리가 배우는 방식
  2022   React 18
  2024   React 19 (12월) - 이 수업의 버전

▶ 포인트
  "React는 새로운 마법이 아니라, jQuery 시대의 고통(화면과 데이터 동기화)을 해결하려고 나왔다."
  → 학생들은 방금 jQuery까지 배웠으므로 이 고통을 이미 체감한 상태다.

4. React의 핵심 아이디어 4가지 (12분)
=====================================================================
< 4-1. 선언형 (Declarative) UI >  ★ 가장 중요

  명령형 (Imperative) : "어떻게" 바꿀지 순서대로 지시한다.  - 바닐라 JS, jQuery
      1) 버튼을 찾아라  2) 클래스를 바꿔라  3) 숫자를 찾아라  4) 글자를 바꿔라 ...

  선언형 (Declarative) : "무엇이" 보여야 하는지만 적는다.    - React
      "liked가 true면 빨간 하트, 숫자는 likeCount"

    function LikeButton() {
      const [liked, setLiked] = useState(false);
      const [count, setCount] = useState(10);

      return (
        <button onClick={() => { setLiked(!liked); setCount(liked ? count - 1 : count + 1); }}>
          {liked ? "❤️" : "🤍"} {count}
        </button>
      );
    }

  판서 :  UI = f(state)
         "화면은 데이터(state)를 넣으면 나오는 함수의 결과다."
         데이터만 바꾸면(setState) 화면은 React가 알아서 맞춘다.

  비유 : 택시 기사에게
         명령형 = "직진하다가 두 번째 신호에서 좌회전, 300m 가서 우회전..."
         선언형 = "강남역으로 가 주세요." (길 찾기는 기사가 한다)


< 4-2. 컴포넌트 (Component) >

  - 화면을 독립적인 "부품" 단위로 나눈다. 레고 블록처럼 조립한다.
  - 컴포넌트 = 화면 모양(HTML) + 동작(JS) + 데이터(state)를 한 덩어리로 묶은 것
  - 한 번 만들면 여러 곳에서 재사용 : <ProductCard /> 를 상품 목록, 장바구니, 추천 영역에서 사용

  판서 : 인스타그램 화면을 박스로 나누기
     App
     ├── Header (로고, 검색, 아이콘)
     ├── StoryList → Story, Story, Story ...
     └── Feed → Post, Post ...
                 └── PostHeader, PostImage, LikeButton, CommentList

  "HTML/CSS/JS 파일을 나누던 방식"  →  "기능(컴포넌트)별로 파일을 나누는 방식"


< 4-3. 단방향 데이터 흐름 (One-way Data Flow) >

  - 데이터는 부모 → 자식으로만 내려간다. (props)
  - 자식이 데이터를 바꾸고 싶으면, 부모가 내려준 함수를 호출해서 "부탁"한다.
  - 장점 : 데이터가 어디서 왜 바뀌었는지 위로 따라 올라가면 찾을 수 있다. (AngularJS 양방향 바인딩의 반성)
  - ch02 props, ch05 state 끌어올리기에서 자세히 배운다.


< 4-4. Virtual DOM과 재조정 (Reconciliation) >

  1) state가 바뀌면 컴포넌트 함수를 다시 실행해서 "새 가상 화면(JS 객체)"을 만든다.
  2) 이전 가상 화면과 비교(diff)해서 바뀐 부분을 찾는다.
  3) 실제 DOM에는 바뀐 부분만 반영한다.

  판서
     state 변경 → 새 Virtual DOM ──비교──▶ 이전 Virtual DOM
                                  │
                                  ▼
                       실제 DOM에는 바뀐 <span>만 수정

  ※ 자주 하는 오해 : "Virtual DOM이라서 바닐라 JS보다 빠르다"
     → 정확하지 않다. 잘 짠 바닐라 코드가 더 빠를 수 있다.
     → React의 진짜 가치는 "개발자가 신경 쓰지 않아도 적당히 빠르고, 버그가 적은 코드"를 쓰게 해 주는 것.
     → 실제로 Svelte처럼 Virtual DOM 없이 같은 목표를 이루는 도구도 있다.

5. HTML도 컴포넌트를 만들 수 있다 - Web Components (10분)
=====================================================================
▶ 질문 던지기
  "React 없이 HTML만으로는 <product-card> 같은 나만의 태그를 못 만들까?"
  → 만들 수 있다! 브라우저 표준 기술 "Web Components"

< 5-1. Web Components를 이루는 3가지 기술 >

  1) Custom Elements : 나만의 HTML 태그를 정의한다.
       customElements.define("product-card", ProductCard);
       - 이름에 반드시 하이픈(-)이 있어야 한다. (기본 태그와 겹치지 않게)  <productcard> X
  2) Shadow DOM      : 컴포넌트 안의 HTML/CSS를 바깥과 격리한다.
       - 안의 .title 스타일이 바깥 .title에 영향 X, 바깥 CSS도 안으로 못 들어옴 (스타일 충돌 해결)
  3) HTML Template / Slot : 재사용할 HTML 틀과, 바깥 내용을 끼워 넣을 자리
       - <slot> 은 React의 children 과 비슷하다.

< 5-2. 시연 : 00_web_component_demo.html >

  ▶ 시연 1 : <hello-message> 를 2번 사용 → 같은 문구 2개 (나만의 태그 + 재사용)
  ▶ 시연 2 : <product-card name="텀블러" price="12000"> → 속성만 바꿔서 카드 3개 (React의 props와 같은 역할)
  ▶ 시연 3 : 페이지 제목 .title은 빨간색, 카드 안 .title은 파란색 → 개발자 도구에서 #shadow-root 확인
  ▶ 시연 4 : [텀블러 가격을 15000으로 변경] → 속성은 바뀌었는데 카드 가격은 그대로
             → "데이터가 바뀌면 화면을 다시 그리는 코드를 직접 써야 한다" = jQuery 시절과 같은 문제
             → React는 state만 바꾸면 자동으로 다시 그린다. (4-1 선언형으로 연결)

  핵심 코드 (가장 간단한 형태)

    class HelloMessage extends HTMLElement {
      connectedCallback() {                     // 화면에 붙을 때 실행
        this.textContent = "안녕하세요!";
      }
    }
    customElements.define("hello-message", HelloMessage);   // 태그 이름에 - 필수

    <hello-message></hello-message>

  React로 쓰면

    function HelloMessage() {
      return <p>안녕하세요!</p>;
    }

    <HelloMessage />

< 5-3. 그럼 React는 왜 필요한가? - 비교 >

  | 비교             | Web Components                       | React                                    |
  | 정체             | 브라우저 표준 (설치 필요 없음)         | JavaScript 라이브러리                     |
  | 재사용 컴포넌트   | O (Custom Element)                   | O (함수 컴포넌트)                          |
  | 스타일 격리       | O (Shadow DOM, 강력함)                | 기본 X → CSS Module, styled-components 등  |
  | 데이터 → 화면 갱신 | 직접 render 코드 작성 (명령형)         | state만 바꾸면 자동 (선언형)               |
  | 데이터 전달       | 속성은 문자열만 (객체, 함수 전달 불편)  | props로 객체, 배열, 함수 모두 전달          |
  | 생태계            | 상대적으로 작음                        | 라우터, 상태 관리, Next.js 등 매우 큼        |
  | 잘 맞는 곳        | 디자인 시스템, 여러 프레임워크에서 같이 쓰는 위젯 | 데이터가 자주 바뀌는 웹 애플리케이션 |

  정리
  - "컴포넌트로 재사용한다"는 아이디어 자체는 HTML 표준에도 있다.
  - React의 차별점은 컴포넌트 그 자체보다 "state가 바뀌면 화면이 자동으로 따라온다(선언형)"는 것.
  - 둘은 경쟁 관계만은 아니다. React 19부터 React 안에서 Custom Element를 쓰는 지원이 좋아졌다.
    (회사 디자인 시스템을 Web Components로 만들고, 그것을 React 앱에서 가져다 쓰는 경우도 있다)

6. React 생태계와 이 과정의 로드맵 (5분)
=====================================================================
< 라이브러리 vs 프레임워크 >
  - React는 "화면(UI)"만 담당하는 라이브러리다.
  - 나머지는 필요한 것을 골라서 붙인다.
      주소별 화면   → React Router (ch08)
      스타일        → styled-components (ch09)
      전역 상태     → Context API (ch10), useReducer (ch11), Redux (ch12)
  - 이것들을 처음부터 한 세트로 묶어 둔 "프레임워크" → Next.js (next-lessons 프로젝트)

< 개발 도구 >
  - 브라우저는 JSX를 모른다. → Vite가 JSX를 일반 JS로 바꿔서 보여 준다.
  - 예전에는 create-react-app(CRA)을 썼지만 2025년에 지원 종료 → Vite 사용
    (자세한 차이는 학생용 "00_개발환경_설치.txt" 5번)

< 다른 선택지도 있다 >
  - Vue.js    : HTML 템플릿에 가까운 문법, 배우기 쉬움
  - Angular   : Google, 기업용 대형 프레임워크 (TypeScript 필수)
  - Svelte    : 빌드할 때 최적화, Virtual DOM 없음
  → 국내외 채용 공고와 자료 양에서 React가 가장 많이 쓰이는 편이라 이 과정은 React로 진행한다.
  → 원리(컴포넌트, state, 단방향 흐름)를 이해하면 다른 도구도 금방 배운다.

< 이 과정의 로드맵 > (판서)
  ch01 JSX → ch02 props → ch03 state/이벤트 → ch04 목록 → ch05 state 끌어올리기
  → ch06 useEffect/useRef → ch07 종합 할 일 앱

7. 정리 / 예상 질문 (3분)
=====================================================================
< 세 줄 정리 >
  1. React는 "데이터가 바뀔 때 화면을 맞추는 일"을 대신해 준다. (UI = f(state))
  2. 화면을 컴포넌트로 나누고, 데이터는 위에서 아래로 흐른다.
  3. 컴포넌트 아이디어는 Web Components에도 있지만, React는 선언형 갱신과 큰 생태계가 강점이다.

< 예상 질문 >
Q. jQuery와 바닐라 JS는 이제 필요 없나요?
A. React도 결국 DOM과 JS 위에서 동작한다. 이벤트, 배열 메서드(map, filter), 비동기(fetch)를
   그대로 쓴다. 지금까지 배운 JS가 React 실력의 기본기다.

Q. React가 HTML 파일을 대신하는 건가요?
A. index.html은 하나만 있고, 그 안의 <div id="root"> 에 React가 화면을 그려 넣는다. (SPA)
   ch01 첫 시간에 main.jsx → App.jsx 흐름으로 바로 확인한다.

Q. JSX는 HTML인가요?
A. HTML처럼 생긴 JavaScript 문법이다. 그래서 class 대신 className, 태그는 반드시 닫기 등
   규칙이 조금 다르다. (ch01에서 다룬다)

Q. Virtual DOM 때문에 React가 무조건 빠른 거죠?
A. 4-4 참고. "편하게 짜도 충분히 빠르다"가 정확한 표현이다.

Q. Web Components가 표준이면 그걸 배우는 게 낫지 않나요?
A. 5-3 표 참고. 재사용 + 스타일 격리는 훌륭하지만, 데이터가 자주 바뀌는 앱을 만들 때는
   화면 갱신 코드를 직접 써야 해서 jQuery 시절의 문제가 다시 생긴다. 실무 수요도 React가 훨씬 많다.
